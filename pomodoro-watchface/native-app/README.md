# Native app injection (corrected architecture)

## How "watchface → native app" actually works

My first implementation shipped the Pomodoro as a **Lua watchface**. That is the
wrong layer for what you asked for. What other developers do (see
[Searchstars/Canopus-Module-BluetoothAudio](https://github.com/Searchstars/Canopus-Module-BluetoothAudio),
`README.md → 设备端安装（通过表盘）` and `Canopus.toml → [native_app]`) is:

```
安装表盘 (install watchface)                ──►  .face 包，只是个"投递器"
  └─ 用户在表盘列表点它，Lua 运行一次
       └─ Lua 用普通 io.open 把 签名模块载荷 (CMI1) 提交到
          /data/canopus/inbox/              ──►  Canopus 管理器 watchface 常驻监听
             └─ 管理器校验签名 / 目标 / 哈希
                └─ insmod 加载 ELF 内核模块 (NuttX binfmt module)
                   └─ 模块的 canopus_module_descriptor 里声明 native app
                      └─ 管理器调用 publish_native_app_stage(1):
                            app_install(&launcher_app_descriptor, pages[], n)
                         publish_native_app_stage(2):
                            launcher_add(APP_ID)
                         ──►  应用列表出现"番茄钟"，带页面生命周期回调，
                              和系统应用同层运行 (page framework, 非 Lua)
```

Key evidence from the BluetoothAudio module source:

- `Canopus.toml`
  ```toml
  [native_app]
  enabled = true
  app_id = "org.canopus.bluetooth-audio"
  name = "耳机"
  entry = "canopus_module_descriptor"
  role = "standalone"
  ```
  and its `[capabilities]` include `native-app.register`, `launcher.entry`,
  `ui.dispatch` — i.e. the framework ABI exposes exactly these primitives.
- `crates/bluetooth-audio-device/src/module.rs`
  - `ModuleDescriptorV1` with `FLAG_HAS_NATIVE_APP | FLAG_NATIVE_APP_STANDALONE
    | FLAG_REGISTERS_LAUNCHER_ENTRY | FLAG_REQUIRES_UI_DISPATCHER`
  - `canopus_mod_publish_native_app_stage(ctx, stage)` → stage 1 registers app +
    pages, stage 2 adds the launcher entry.
- `crates/bluetooth-audio-device/src/target/native_app.rs`
  - `app_install(&launcher_app_descriptor, [*page_descriptor; N], N)` then
    `app_lookup(APP_ID)` then `launcher_add(APP_ID)`.
  - `firmware_page_descriptor` lifecycle callbacks the firmware calls natively:
    `on_signal / on_create / on_resume / on_pause / on_destroy` (+ `on_ui_destroy`
    on Band 11) — these are real C-level pages, **not** Lua.
  - Fixed-size app id (`APP_ID: u16 = 0x00CB`), package
    `com.canopus.headphones`, launcher icon path under `/data/canopus/…`.
- Constraint stated by the same project: calling these firmware interfaces
  requires **per-device/per-firmware resolved addresses** (target pack), the
  Canopus framework itself is **closed source**, and module payloads are
  **signed (CMI1)** with a dev/prod key.
- **Correction (verified against the upstream README):** that project's
  supported targets are Band 10 Pro `3.101.036`, Band 10 Pro `3.101.043` and
  Band 11 `4.100.139`. **Mi Band 9 Pro `3.1.175` is not a Canopus target.**
  The framework selects a private ABI backend from `targets/<target-id>.env`
  and fails closed for an unknown target, so a nine-pro pack would have to be
  authored from scratch — which is what
  [`../native-app/targets/xiaomi-band-9-pro-3.1.175.md`](targets/xiaomi-band-9-pro-3.1.175.md)
  (generated by `../tools/target_pack.py`) now provides the static-analysis
  half of.

### What lives on this firmware (verified in vela_ap.bin, 3.1.175)

- NuttX 10.3.0 kernel with a full task/group/spawn model (`group/*`,
  `task/task_posixspawn.c`) and NSH present as a **builtin** (`nsh_main`).
  It nevertheless has **no loader at all**: zero occurrences of `0x7fELF`,
  `binfmt`, `NXFLAT`, `insmod`/`rmmod`, `dlopen`/`dlsym` or the
  `CONFIG_BINFMT`/`CONFIG_MODULE` knobs in `vela_ap.bin` *or*
  `vela_factory.bin`. `LUA_CPATH=…?.so` is Lua's stock default string, and
  `package.loadlib` needs the absent `dlopen`.
- The one native bridge that *is* present is AIOTJS's
  (`jse_nativeproxy.cpp`, `NativeProxy`, `__folme_native_require__`, the
  ``native://`` URI regex) — a JS→native call channel inside the quickapp
  engine, with no dynamic loading involved.
- See [`../docs/userland-loader-blueprint.md`](../docs/userland-loader-blueprint.md)
  for what the missing loader implies and the four candidate channels to work
  around it.
- Launcher / page manager: `app_launcher_add`, `launcher_page_*`,
  `sort_apps`, `create_app_icon`, `pagemanager` (`register page … must be
  specified`, `app [%s] not stopped(%d), ignore prelaunch`) — the things
  `publish_native_app` manipulates.
- Xiaomi's own sanctioned "third-party native app" channel: the quickapp (rpk)
  pipeline — `quickapp_install_locally`, `ferry::PackageManager::installRpk`,
  `manifest.json` + signature verification (`app_verify_*`,
  `app_block.signature_block`, mbedtls), install dirs
  `/data/quickapp/app/<pkg>/`, config `/data/app/quickapp/config.json`,
  fingerprint db `/quickapp/rpk_info.json`, and icons fetched from the phone.
  This channel is phone-app-driven and Xiaomi-signed; it is the path the
  built-in 番茄钟 (`com.xiaomi.miwear.tomatotimer`) itself sits next to.
- Lua surface: `luaopen_{lvgl,dataman,topic,vibrator,screen,navigator,
  activity,miwear}` — **no `luaopen_os` / `luaopen_io` in the AP image**, and
  the stock watchface scripts use neither. Watchface Lua is sandboxed; it is
  only the *delivery vehicle* (io-based install request submission happens via
  the Canopus manager's own file staging, see below).

## Honest bottom line for Band 9 Pro 3.1.175

| Path | Native app in launcher? | Reproducible without Xiaomi keys? |
|---|---|---|
| Lua watchface (what I shipped first) | ❌ (watchface list only) | ✅ done, `dist/Pomodoro.face` |
| Quickapp `.rpk` | ✅ | ❌ Xiaomi signing chain + phone app transfer |
| **Canopus module** (KernelSU-analogue) | ✅ (`app_install` + `launcher_add`) | ❌ framework + target pack are private, **and 3.1.175 is not a supported Canopus target** (upstream lists Band 10 Pro `.036`/`.043` and Band 11 `.139`) |
| Canopus-style module on *our own* supervisor | ✅ same ABI | ⚠️ needs a one-time native bootstrap on this firmware — no `binfmt`/`insmod`/`dlopen` exists (see the loader blueprint) |

So the correct deliverable mirrors the BluetoothAudio repo's layout: a Canopus
module (Rust, `no_std`, cortex-m33) that registers the Pomodoro native app, plus
a **one-shot installer watchface** that submits the signed CMI1 payload. This
directory contains that module skeleton and the installer watchface; building
the actual `pomodoro.bin` ELF requires the private Canopus framework repo
(`AstralSightStudios/Canopus`) placed side-by-side, per its README.

## Notifications

The user-visible request "支持系统通知（如果可用）". Both halves now have firmware
addresses in the target pack:

- **Haptics** — `miwear_vibrator_run` `0x2C4602CC` (57 callers: reminders,
  alarms, UI) and `miwear_vibrator_cancel` `0x2C460388`; `lua_vibrator_start`
  `0x2C46E5C8` is the Lua binding of the same service and documents the
  pattern argument.
- **Notification tray** — the firmware does have the full API after all:
  `lvx_notification_init_message` `0x2C45F390`,
  `lvx_notification_insert_message` `0x2C4F1C44` (13 callers),
  `lvx_notification_insert_many_message` `0x2C2B4D58`,
  `lvx_notification_remove_message` `0x2C4ED540`,
  `lvx_notification_remove_all_appid_message` `0x2C4DFB4E`,
  `lvx_notification_update_message_icon` `0x2C2AFEAC`, plus
  `lvx_notification_start_reminder` and `notification_manager`. These are
  **unreachable from watchface Lua** (no `io`/`os`, no notification binding),
  which is why the watchface only vibrates — but a native module can push a real
  tray notification. `notifications.tray` is therefore a **required**
  capability in `canopus.toml`, and the message struct offsets are recorded in
  the target pack's field-offset section (from the construction code in
  `lvx_notification_init_message` and the parameter writes in
  `lvx_notification_insert_message`).
